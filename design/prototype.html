The composite

Where each of the three went

The frame

was Console

Sidebar, one page at a time, config file on the right. You are always somewhere specific — the whole server, all maps, or one map — and the sidebar says which. Nothing is nested more than one level deep.

The rotation page

was Sheet

Clicking All maps gives you a table instead of a form, because sixteen maps in a form is sixteen visits. Click a row and you drop into that one map, which is the same pages again, scoped smaller.

The coloured dots

was Stack

The layer stack shrank to one popover per setting. You only need it when a value surprises you — and then it tells you exactly which preset or mutator is responsible, and lets you take it back.

Decisions

What I've settled on, and why

You made the important call — the schema lives in the Alpine repo, pinned by submodule. Everything below follows from that.

The schema is TOML, and half of it is generated you asked: TOML or not?

Yes to TOML, but split in two

Using TOML means the builder needs exactly one parser, which it already needs for opening someone's existing config. It is the format Alpine's devs already write. Same syntax, different vocabulary — a schema needs types, ranges, units, help text and dependencies that a config has no use for.

The split matters more than the format. Authored files hold the things only a person can write: the plain‑English label, the help sentence, which page a setting belongs on, the unit to show it in. Generated files hold everything a machine can read out of the source: the key list, types, defaults, the fourteen game types, the twenty mutators with their options and client version floors, and every weapon, item and character name.

Nothing about this touches the Alpine devs you asked: can CI just do it?

Yes — the generator lives in the builder repo and runs on every build

I had this the wrong way round last time. There is no checked‑in schema in the Alpine repo, no regenerate step, no failing check for anyone writing server code. Builder CI checks out the pinned submodule, reads the source, and produces the schema fresh each build. An Alpine dev adds a setting exactly the way they do today and never hears about this tool.

I also need to correct the mechanism. I said the generator could call Alpine's own functions and diff the result — it can't. apply_instagib reads rf::rail_gun_weapon_type, which only exists once the game is loaded, and the codebase is a Windows game patch that will not build on a plain CI runner. So the generator parses the source instead of running it. That works well for most of what we need and not at all for one part, so here is the honest split.

Parsed from the source

Setting names, types and defaults; all fourteen game types; the whole mutator table with its options, labels, client version floors and game type restrictions. These are flat literals and regular declarations — a small parser reads them reliably, and builder CI fails loudly if a pattern ever stops matching.

One trap worth knowing: config names and code names are not always the same. flag_return_time is seconds in the file and milliseconds in the struct, and spawn_armor is spawn_armour in the code. So the parser has to read the config parser, not the struct.

Written by hand, checked by CI

What each mutator actually changes. Those live inside function bodies, so parsing them is guesswork. Twenty short entries in the builder repo instead, and CI compares them against the parsed mutator list — a new mutator with no entry fails the build.

If one goes stale the cost is a popover that under‑explains, not a broken config. The file only ever contains what you set.

Not in the Alpine repo at all

Weapon, item and character names. Those come from the game's own table files at runtime, so no amount of parsing finds them. Either the builder carries a list taken from the stock game data, or those fields stay free text with a “that name is not one we recognise” warning. Worth your call.

It resolves — but no game logic in JavaScript you left this one to me

Resolve, from generated tables only

Without resolution, every dot in the prototype is a lie and the tool cannot tell you that Instagib just overrode your starting weapon. That is worth having. What is not worth having is a second implementation of Alpine's rules in JavaScript, quietly going out of date.

Because the effect tables are generated, resolving is just merging tables in a fixed order — no logic to reimplement. Where a mutator does something that is not a value, like removing pickups, the schema says so in a sentence and the tool prints that sentence instead of pretending to compute it. You can see this in the popover for the starting weapon.

Preset authoring is not a mode you left this one to me

It is an export option

The old builder had an “is a preset” checkbox that hid half the tool, which meant deciding up front what you were making. But a preset is just the Game rules pages on their own. So Download offers the whole server config or just the game rules, and opening a preset file drops you straight into Game rules with the rest of the sidebar dimmed. Nothing to decide in advance, nothing to undo if you change your mind.

The map picker is live, always

No snapshot — and typing a file name stays a first‑class option

Dropping the baked snapshot makes one thing non‑negotiable: without a CORS header the picker cannot work at all. The page is static and has no server in between, so the browser makes the request directly and will refuse to read the response without one. Everything else on the list below is an improvement; that one is the difference between the feature existing and not.

So the picker leads with search, and keeps a plain type a file name field next to it rather than hiding it behind a failure. That covers total conversion maps, anything not on FactionFiles, and the person who already knows what they want to type — which is how the tool has worked until now.

If you want to add API surface for the map picker, this is what would make it work well:

  • A CORS header allowing the built page's origin. Nothing else on this list matters without it — there is no server between the page and FactionFiles.
  • A search endpoint returning JSON per map: the .rfl file name, display name, author, description, file size, upload date, thumbnail URL and download URL.
  • The mode a map was made for, and its intended player count, if FactionFiles knows them. That is what lets the builder warn you that a CTF map is scheduled as Deathmatch.
  • Pagination, so a broad search does not pull the whole archive.

The pipeline

How a new Alpine setting reaches the tool

The whole update process is one commit, and it is yours. Alpine’s side of this diagram is deliberately empty.

Alpine repo

A setting is added

Someone adds a key to the rules struct and parses it in dedi_cfg.cpp, exactly as they do today. No schema to update, no check to satisfy.

Alpine release

A tag is cut

Nothing changes for the builder until someone points it at the new tag, so the tool always matches a real release rather than whatever is on main.

Builder repo

You bump the submodule

One commit. This is the entire manual step, and it is on your side.

Builder CI

Reads, builds, deploys

Parses the pinned source into a schema, generates the pages, deploys the static site. If the source changed shape, this is where it breaks — on your build, not on theirs.
